Technical Documentation

Safe Route AI

Security threat reporting and route advisory for humanitarian teams operating in North Eastern Kenya.

Report → Analyse → Verify → Alert → Protect

A mobile application that centralises security incident reporting, uses AI to classify reports and detect duplicates, requires human verification before any threat goes live, and delivers location-aware alerts and route advisories to the workers those threats affect.

1. The Problem and the Response

Humanitarian organisations in Garissa, Wajir and Mandera counties operate in an environment of armed incidents, road ambushes, banditry and inter-communal conflict. Security information exists, but it moves by phone call, WhatsApp group and word of mouth. Three failures follow from that:

  • Information does not reach the people it concerns. A road ambush is known to one team and unknown to the convoy that leaves an hour later.
  • Unverified rumour circulates as fact. A second-hand report can shut down a corridor that was never actually dangerous.
  • Nothing is auditable. After an incident, there is no record of who knew what, or when.

Safe Route AI addresses these with a single closed loop.

StageWhat happensWho acts
ReportFree-text description, optional photo, GPS captured automatically. Works with no connectivity.Humanitarian worker
AnalyseAI classifies threat type and severity, suggests an alert radius, and flags likely duplicates.System (advisory only)
VerifyAn officer confirms or overrides every field. Nothing reaches the field without this step.Security officer
AlertFan-out to affected workers by organisation, partnership, proximity and declared region.System
ProtectThreat map, route risk comparison, one-tap SOS.Humanitarian worker
The central design decision Verification by a human is mandatory and cannot be bypassed. The AI proposes; a security officer decides. This is enforced at the database level, not merely in the interface — a client that bypassed the app entirely still could not publish an unverified threat. Everything else in the system is arranged around protecting that property.

ConstraintConsequence for the design

2. Roles and Separation of Duties

Three roles, with boundaries enforced by Row Level Security in PostgreSQL rather than by hiding controls in the interface.

Read the audit logNoYesYes
Why an admin cannot verify a report An admin creates the officer accounts. If the same person could also exercise an officer's authority, a single account could both grant the power to publish threats and use it — and the audit trail would no longer show an independent decision. Splitting the two means every verified threat carries the name of someone who was appointed to that role by a different person.

The same reasoning excludes officers from creating invites, and excludes everyone from writing to the audit log.

Cross-organisation sharing

Organisations may declare cross-share partnerships. Partnerships are reciprocal by construction — enforced by a database trigger that mirrors the relationship — because a one-way arrangement would let an organisation consume another's threat intelligence without contributing any.

DataShared with partners?
Verified threat reportsYes
Safety advisories (opt-in per advisory)Yes
Pending, unverified reportsNo
Staff directoryNo
Live SOS locationsNever

A live worker position is the most sensitive datum in the system. Partner organisations share threats; they do not share people.

The transport seam

The application supports two interchangeable backends behind one interface. Screens import an endpoint and never learn which answered:

export const reportsApi = API_MODE === 'supabase'
  ? supabaseReportsApi
  : mockReportsApi;

The mock is a first-class implementation, not a migration stub. It runs entirely on-device with a deterministic dataset, needs no network and no project, and is switched on with a single environment variable. It exists so the application can be demonstrated, reviewed and developed without infrastructure — and so the offline paths can be exercised deliberately.

Data flow: filing through to alerting

Worker files a report
  → client mints a UUID; zod validates the draft
  → OFFLINE?  outbox (persisted) → backoff retries → same id, no duplicate
  → ONLINE?   INSERT ... status 'pending'   [RLS forbids any other status]
              → classifier writes ai_suggestions   [service role only]
              → Realtime pushes it to the officer queue

Officer verifies
  → RLS: officer role required, own or partner organisation
  → officer-confirmed columns written; ai_suggestions left untouched
  → trigger stamps verified_by / verified_at from the JWT, not the payload
  → trigger appends an audit entry naming every overridden field
  → fan_out_alert() applies the four rules in one SQL statement

Worker receives
  → Realtime toast + OS notification + persistent feed row
  → the feed row carries the reasons it matched

Cross-platform mapping

ThreatMap has two implementations behind one props contract: react-native-maps on device, and an SVG schematic on web, where that library has no build. The web version draws real road corridors, real place names and an equirectangular projection — every coordinate, radius and route on it is accurate; it simply has no tiles. Screens import ThreatMap and never learn which they received.

Geography

Positions are stored as PostGIS geography(Point, 4326) with GiST indexes, which is what makes proximity queries fast. Because PostgREST serialises geography as WKB hex, generated lat/lng columns expose plain numbers to clients. They are STORED and recomputed by Postgres on every write, so they cannot drift from the geometry they derive from.

Why Row Level Security carries the weight

The application ships with a public API key embedded in the bundle. Anyone with the installed app can extract it. That is by design and is safe only because every table denies by default and opens only what a given authenticated role needs. The client-side role checks are a courtesy that produces better error messages; the policies are the actual guarantee.

Policy helper functions are SECURITY DEFINER with a pinned search_path. Definer is required because a policy on profiles that itself queries profiles would recurse infinitely; the pinned search path prevents a caller shadowing public with their own tables.

Reporter anonymity

Protecting reporters from retaliation is a safety requirement, not a privacy preference. RLS controls which rows are visible but cannot blank a column, so peer-facing access goes through a dedicated view:

  • Reporter identity replaced with null
  • Photograph withheld
  • Position offset by 50–300 m — deterministic, so the pin does not wander between loads; far below any alert radius, so the warning stays accurate
  • Your own reports are always returned in full

Organisations operating in especially sensitive contexts can additionally hide reporter identity from their own officers.

Authentication

ControlBehaviour
Account creationInvite-gated. A database trigger validates the code inside the signup transaction — an invalid code leaves no orphan account.
Password resetSix-digit code by email, single-use, time-limited, attempt-capped.

Audit trail

The audit log has no insert, update or delete policy. Entries are appended exclusively by SECURITY DEFINER triggers, so no client can forge or suppress one. Append-only is the property that makes it evidence rather than a changelog.

6. The Alert Fan-Out

A worker is alerted when any of four conditions holds. All four are evaluated in a single SQL statement using PostGIS.

#ConditionRationale
1Same organisation as the reportColleagues share an operating picture.
2A cross-share partner of the reporting organisationThreats do not respect agency boundaries.
3Last known position inside the alert radiusProximity is the most urgent case.
4Threat falls inside a declared operating regionCovers a worker who travels there but is elsewhere today.

Each notification carries the reasons it matched, and the interface displays them. An alert that explains itself — "you are inside the 12 km radius" — is actionable in a way that an unexplained one is not.

Deliberate exclusions

  • The reporter is never alerted about their own report. They already know; alerting them is noise, not safety.
  • Admins are excluded by default. They manage the organisation and are not in the field. Paging them on every incident trains everyone to ignore alerts.
  • Quiet hours are respected — except for critical.
  • "Only critical" does not suppress proximity. Anything inside the radius reaches the user regardless of preference, because that is about their own safety rather than their inbox.
Preview before sending Before an officer commits, the interface shows exactly how many people will be notified, computed by a function that applies the same four rules as the fan-out itself. Widening a radius from 6 km to 20 km visibly changes the count from four people to thirty-one. The number shown is the number that will actually be reached — not an estimate that can drift.

7. AI Classification

On submission, a report is analysed for threat type, severity, priority, a suggested alert radius, and likely duplication. The output is written to ai_suggestions and is never written to the officer-confirmed columns.

Advisory by construction

PropertyHow it is guaranteed
AI cannot publish a threatRLS forbids a non-officer changing status; the insert policy forces pending.
AI output cannot be editedA trigger rejects any client write to ai_suggestions, including the first.
Proposal and decision stay separableStored in different columns; the audit entry records which fields were overridden.
Classification never blocks a reportRuns after the row is committed. A failed classification leaves the report fully reviewable.
Low confidence is stated plainlyA "needs more detail" flag is surfaced rather than smoothed over.

Duplicate detection

Two stages, mirroring how the production function is intended to run:

  1. Geo and time pre-filter in SQL — reports within roughly 5 km and 12 hours, using the spatial index.
  2. Semantic comparison over that shortlist, scoring lexical overlap, proximity and recency with smooth decay. Two reports of the same ambush are rarely pinned to the same metre.

Only a strong, corroborated match is flagged, and a flag is a suggestion: the officer sees both reports side by side and decides. Confirming a duplicate closes the second report without issuing a second alert.

Oversight metrics

The application reports an AI agreement rate — how often officers accepted a suggestion unchanged — and flags rates above 92% as a concern. Too low means the model is noise. Suspiciously high suggests rubber-stamping, which would make the human verification step decorative. The metric is shown to officers as a mirror, not only to management.

8. Offline Resilience

Coverage gaps are the operating norm, not an edge case. Several architectural decisions exist only because of this.

MechanismBehaviour
Client-minted identifiersThe device generates a UUID before any network call. It doubles as the idempotency key, so a submission retried after a timeout cannot become a second report.
Priority orderingSOS always jumps ahead of reports and sends the instant signal returns, surviving app restarts.
Capped backoff with jitterPer item, so one poisoned entry cannot block the queue. Jitter prevents a convoy regaining signal simultaneously from stampeding the server.
Non-retryable failures parkA malformed payload or permission error cannot be fixed by waiting. It is marked failed and surfaced in the Outbox rather than retried indefinitely.
Honest confirmationThe interface says "saved on this device" — never "sent" — until the server has it.
Why caching is a safety feature here A worker who opens the threat map in a dead zone must still see the threats verified while they had signal. A blank map reads as "all clear" — the most dangerous thing this application could say. Caches therefore serve stale data with a visible "last updated" marker rather than showing an empty state or a spinner.

Named cache policies balance freshness against offline usefulness: threat data is briefly fresh but retained for a week; the officer queue is near-live; analytics tolerate being a minute old. A development switch simulates loss of signal so every queue, cache and retry path can be exercised without leaving the building.

9. Safe Route Advisory

A worker enters origin and destination and receives two or three candidate routes, each scored by the verified incidents near it.

Only verified reports count. An unverified rumour must not be able to close a road.

Analysis

For each candidate polyline, PostGIS finds every verified threat within a configurable buffer of the line (ST_DWithin against the route geography). Each is scored with two independent decays:

  • Recency — exponential, roughly a fortnight half-life
  • Proximity — linear across the buffer

A critical ambush 200 m off the road last night therefore weighs far more than the same event 1.9 km away a month ago, and the score says so.

Presentation

Routes are ranked with incident count, worst severity, distance and estimated time. A route carrying a critical incident inside the buffer is never recommended, whatever its aggregate score.

What the advisory does not know Unreported incidents, checkpoints established this morning, road and vehicle condition, and escort arrangements are all invisible to it. The interface says so explicitly. The output ranks options and explains why; it never chooses, because the person in the vehicle knows things the application does not.

10. SOS

The design constraint: the person triggering this may have seconds, one hand, and no signal.

DecisionReasoning
Hold, not tapBroadcasting a live position cannot be undone quietly. A 1.6-second hold with a progress ring and haptic feedback is deliberate but still usable under stress.
Always reachablePresent on every worker screen. Nothing is permitted to obscure it, including transient messages — which is why notifications appear at the top of the screen.
Queued firstRecorded on the device before any network attempt, and sent the instant signal returns.
One live event per workerA second trigger escalates the existing event rather than fragmenting the officer's view across two cards.
Independent position pingsEach is separately retryable. A dropped ping never invalidates the event.
Acknowledgement is distinct from resolutionThe worker most needs to know a human has seen it. Acknowledgement is one tap and is timed as its own metric.

Officers see live events with the position track, add notes visible to the worker, and resolve with a required note. The worker may stand down their own event. The full timeline is retained for post-incident review.

11. Design System

Dark-first. The application is used at night, in vehicles and in low-light compounds, where a bright screen is both a comfort problem and a personal security problem. Both schemes are fully defined; no colour falls back to a guess.

The severity palette was computed, not chosen

Severity is the fastest signal in the product, so the ramp was validated rather than eyeballed. An initial palette placed medium and high only ΔE 11.2 apart in normal vision — two adjacent severity levels that look alike, in a safety application. The ramp was re-stepped until both schemes passed:

SchemeCVD separationNormal visionContrast
DarkΔE 12.9 (deutan)ΔE 16.3All ≥ 3:1
LightΔE 13.9 (protan)ΔE 15.5All ≥ 3:1

Severity is additionally encoded by pin size on the map and is always paired with its word, so the level never rests on colour alone — which matters for colour-blind users and in direct sunlight, where hue separation collapses.

Other conventions

  • Minimum 44 px touch targets — field use means gloves, motion and hurry
  • Haptics as an accessibility feature: confirmation you can feel without looking
  • Empty states distinguish "nothing exists" from "nothing matches your filter"
  • Charts follow one axis, never two; colour never carries identity alone
  • Accessibility roles, labels and live regions throughout

Configuration

Environment values are injected at build time through a dynamic Expo config.

Critical Variables prefixed EXPO_PUBLIC_ are inlined into the application bundle and are readable by anyone holding the installed app. Only the public API key belongs there. The service role key — which bypasses Row Level Security entirely — and the AI provider key must exist only as server-side function secrets, and must never appear in the repository.

Operational notes

  • Backups. The audit log is the accountability record; point-in-time recovery should be enabled before real users.
  • Project pausing. Free-tier projects pause after inactivity. Unacceptable for a safety application — a paid tier is required in production.
  • Migrations replay cleanly. Verified by applying twice.
  • Email confirmation is currently disabled for demonstration and should be re-enabled, with a deep link, before real users.
  • Not indexed. This is an authenticated tool for named field staff; search visibility is a deliberate non-goal.

14. Known Limitations and Roadmap

ItemStatus
AI classification on new reportsThe classifier is implemented and its output shape is the contract the interface is built against, but it has not yet been deployed as a server-side function. Existing reports carry suggestions; newly filed reports remain unclassified until deployment. Requires a paid AI provider key.
Photograph uploadCapture and queueing work; images are held as local URIs pending object storage.

Suggested sequence

  1. Deploy the classification function — completes the loop for new reports
  2. Object storage for photographs
  3. Push tokens and a development build for background delivery
  4. Enable backups and email confirmation; move off the free tier
  5. Connect a routing provider for road-accurate geometry
  6. Field pilot with one organisation before widening
Closing note The properties this system is built to protect are that no threat reaches the field without a named human approving it, that no reporter is exposed to the people they reported on, and that nothing is silently lost when the network disappears. Every architectural decision documented above serves one of those three. Where a trade-off was made, it was made in their favour.
